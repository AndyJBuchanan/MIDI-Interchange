# Project Brief: MIDI Interchange — Cross-Platform MIDI Assembly & Export Utility
## 1. Objective
Build a lightweight, responsive, standalone desktop application for macOS and Windows that allows users to import MIDI files or drag MIDI clips directly from music applications, assemble and manipulate their contents, select musical ranges on a graphical timeline, and export the resulting MIDI by saving a file or dragging it directly into another application.
Working name: MIDI Interchange
The application is a MIDI interchange and manipulation workspace, NOT a DAW, sequencer, MIDI player or conventional note editor.
Its primary purpose is to eliminate the friction of importing, modifying, trimming and exporting MIDI between applications.
Typical source and destination applications include:

* Steinberg Cubase
* Reason
* RapidComposer 6
* Staccato.ai
* Synthesizer V Studio 2
* Yamaha Omnivocal
* Other applications supporting Standard MIDI Files or external MIDI drag-and-drop

The application should open quickly, respond immediately and require minimal user interaction for common operations.
## 2. Technology Stack
Preferred implementation:

* Python 3.12+
* PySide6 / Qt 6 for the cross-platform desktop GUI
* Mido for MIDI parsing and writing, supplemented by custom code where necessary for lossless event handling
* Python dataclasses for the canonical internal MIDI model
* Custom-painted Qt timeline widget for visualization and interaction
* PyInstaller for packaging standalone macOS `.app` and Windows `.exe` distributions
* pytest for automated testing

Use platform-specific Qt or native OS APIs where required for interoperable drag-and-drop.
Do not introduce a C++ dependency, plugin framework, database, audio engine or elaborate abstraction layer without a demonstrated need.
Keep the MIDI processing engine independent of the UI.
Performance should not be treated as a major obstacle. MIDI files are small by modern standards. Parse and normalize imported data immediately, and operate on the canonical model thereafter.
## 3. Core Design Principles

1. Timeline-first interface. The graphical multitrack timeline is the primary workspace, not an optional visualization.
2. Canonical internal representation. All incoming MIDI data, regardless of source, is converted into a common document model at import.
3. Non-destructive operations. Import, filtering, renaming, range selection and positioning must not modify the original data.
4. Metadata preservation. Preserve all supported MIDI events, including lyrics and other meta-events, even when the application doesn't directly manipulate them.
5. Accumulative importing. Successive imports add material to the workspace rather than replacing existing material.
6. Interoperable drag-and-drop. Dragging MIDI in and out of the application is a fundamental feature, not an optional enhancement.
7. Minimal friction. Avoid unnecessary dialogs, project creation steps, instrument assignment or other DAW-like workflow overhead.
8. Cross-platform. Share as much code as possible between macOS and Windows.
9. Pragmatic implementation. Build working vertical slices. Avoid speculative infrastructure and premature optimization.

## 4. Import Requirements
### 4.1 File Import
Support:

* Dragging `.mid` and `.midi` files from the operating system.
* File → Open.
* Multiple files dropped simultaneously.
* Repeated imports into the same workspace.
* Standard MIDI File formats 0 and 1 as a minimum.

Format 0 files should be represented sensibly in the track-oriented workspace, preserving their original channel and event information.
### 4.2 Direct MIDI Clip Import
Support dragging MIDI clips directly from external applications, particularly:

* Cubase
* RapidComposer 6
* Staccato

These applications already participate in cross-application MIDI interchange.
Implement receiving through the public drag-and-drop mechanisms provided by Qt and the underlying operating system.
Relevant mechanisms include:

* File URLs
* File promises
* Native MIDI data representations
* Multiple drag items
* Platform-specific MIME types and clipboard formats

On macOS, investigate and use the appropriate `NSPasteboard`, `NSDraggingInfo`, Uniform Type Identifier and file-promise APIs.
On Windows, use the corresponding OLE drag-and-drop / clipboard data mechanisms through Qt or native APIs where required.
Do not treat the differences between drag representations as an architectural problem.
They are import-boundary implementation details. Convert incoming material to canonical MIDI immediately.
Where an external application does not expose usable MIDI data, report that limitation clearly rather than silently failing.
### 4.3 Accumulative Import
Each incoming file or clip should add one or more tracks or clips to the current workspace.
For example:

1. Drag a piano clip from Cubase.
2. Drag a bass phrase from RapidComposer.
3. Drag a melody from Staccato.
4. Drag an additional MIDI file containing lyrics and controller data.
5. Select, rename, align and export the assembled material as a single multitrack MIDI file.

Imports may contain one musical track, multiple tracks, or auxiliary tracks holding metadata.
Preserve source track relationships and source identity where possible.
### 4.4 Import Provenance
Retain useful source information, where available:

* Original filename
* Source application
* Original track names
* Original track/channel identifiers
* Original clip position
* Original MIDI timing resolution
* Import timestamp
* Original imported bytes or equivalent raw payload

Source information should be available for inspection without cluttering the main interface.
## 5. Canonical MIDI Document Model
The application should maintain an internal model with the following conceptual structure:
`Workspace → Sources → Tracks → Clips → Events`
#### Events
Represent:

* Absolute musical time
* Event type
* MIDI channel where applicable
* Event payload
* Stable ordering for simultaneous events
* Associated source information

Support:

* Note on/off
* Control changes
* Program changes
* Pitch bend
* Channel pressure and polyphonic aftertouch
* SysEx
* Tempo changes
* Time signatures
* Key signatures
* Track names
* Lyrics
* Text
* Markers and cue points
* Other MIDI meta-events

Unknown or unsupported meta-events should be retained rather than discarded.
#### Timing
Use a consistent canonical musical time representation.
Preserve sufficient precision to avoid introducing timing errors when importing MIDI files with different PPQ resolutions.
A rational tick representation or an appropriate high-resolution internal PPQ may be used, provided conversion is deterministic and lossless where possible.
Retain original timing resolution information.
Support conversion between absolute ticks, bars, beats and subdivisions.
Handle tempo and time-signature changes.
#### Tracks and Clips
Each track should have:

* Unique internal identifier
* Editable name
* Enabled/disabled state
* Source association
* One or more MIDI clips
* Musical position or offset
* Original event data
* Optional colour
* Optional auto-trim setting

Tracks and clips should remain independently manipulable.
#### Tempo Maps
When importing material from multiple sources, do not silently combine conflicting tempo maps.
Maintain an authoritative workspace timing map, with imported tempo information retained.
Provide a sensible initial policy and allow the user to select or adopt an imported tempo map where appropriate.
## 6. Main User Interface
The application should use a compact, single-window layout.
### 6.1 Primary Layout
Suggested arrangement:
#### Top toolbar

* Open/import MIDI
* Save/export
* Undo/redo
* Zoom controls
* Snap controls
* Range management

#### Left track panel

* Enable/disable checkbox
* Editable track name
* Source identification
* Track colour
* Track reorder control
* Remove track

#### Main timeline

* Horizontal bar/beat ruler
* One lane per track
* Rendered MIDI note content
* Multiple editable range selections
* Clip positions
* Metadata indicators

#### Bottom export panel

* Export range selection
* Export layout mode
* Auto-trim options
* Drag-out target
* Save MIDI button

Keep the interface visually clean and functional.
### 6.2 Timeline Rendering
The timeline is a mandatory core feature.
Implement using a custom-painted Qt widget or an equally efficient Qt rendering approach.
Display actual MIDI note events as compact piano-roll-style rectangles within each track lane.
The objective is to visualize musical content and activity, not to edit individual notes.
Include:

* Bar and beat grid
* Musical ruler
* Horizontal scrolling
* Horizontal zoom
* Track lanes
* Note rectangles
* Visible clip boundaries
* Selection range overlays
* Markers or indicators for lyrics and other metadata
* Tempo/time-signature markers where applicable

The timeline must remain responsive while zooming, scrolling and changing selections.
Do not create a separate heavyweight graphical object for every MIDI note unless there is a clear reason to do so.
### 6.3 Range Selection
This is one of the application's most important features.
Users must be able to:

* Click-drag on the timeline/ruler to create a range.
* Drag range boundaries to resize it.
* Drag a range body to reposition it.
* Create multiple independent ranges.
* Select and delete ranges.
* Name ranges optionally.
* Enter precise start/end positions numerically.
* Snap to bars, beats or finer subdivisions.
* Disable snapping when required.

Use half-open intervals internally: `[start, end)`.
This avoids ambiguity at adjacent range boundaries.
Range selection must be independent of track selection.
Users should be able to define several ranges and change enabled tracks without losing their selections.
### 6.4 Track Management
Support:

* Enable/disable individual tracks for export.
* Rename tracks.
* Reorder tracks.
* Remove tracks from the workspace.
* Import additional tracks at any time.
* Adjust imported clip/track positions.
* Preserve auxiliary metadata tracks.

Where feasible, allow individual tracks to be dragged out as MIDI files without changing the global track enable state.
## 7. Export Requirements
### 7.1 Standard MIDI Export
Export Standard MIDI Files, preferably format 1 for multitrack output.
Support:

* Entire assembled workspace
* Selected tracks
* Individual tracks
* A selected time range
* Multiple selected time ranges

Preserve metadata, timing and MIDI event semantics.
Export should not require modifying the underlying workspace.
### 7.2 Export Range Modes
Provide at least three modes.
#### A. Preserve original positions
Export events in the selected ranges while retaining their musical positions.
For example, material selected from bars 17–24 remains at bars 17–24.
#### B. Rebase / concatenate
Move selected material to the beginning of the exported MIDI.
For multiple ranges, concatenate them in the user-defined order, removing gaps between ranges.
#### C. Separate ranges
Export each selected range as a separate MIDI file.
For drag-out, multiple files may be supplied where supported by the destination.
### 7.3 Boundary Handling
Correctly handle events crossing range boundaries.
In particular:

* Notes beginning before the selection and ending inside it.
* Notes beginning inside the selection and ending after it.
* Sustained notes crossing both boundaries.
* Overlapping notes of the same pitch/channel.
* Controller state at the beginning of a selection.
* Tempo and time-signature state at the selection start.
* Lyrics and metadata associated with selected musical material.

Define and document a consistent policy for clipping notes and carrying relevant state into rebased exports.
Avoid stuck notes, incorrect durations and accidental loss of timing context.
### 7.4 Auto-Trim
Support optional removal of leading and trailing silence.
Distinguish between:

* Trimming individual tracks.
* Trimming the assembled output as a whole.

Do not silently destroy relative timing alignment between tracks.
### 7.5 Drag-Out
Users must be able to drag processed MIDI directly into another application.
Support:

* Whole-workspace drag-out
* Selected-range drag-out
* Individual-track drag-out
* Multiple-range export where supported

Generate standard MIDI files or file promises through the operating system's drag-and-drop APIs.
Use temporary files where appropriate.
Ensure temporary files remain available for the lifetime required by the destination application's drop operation.
The export target should be visually obvious.
Where practical, individual named ranges should have their own drag handles.
## 8. MIDI Integrity
Preservation of musical and metadata content is a fundamental requirement.
Avoid reconstructing or simplifying event streams unnecessarily.
Where possible:

* Preserve original event payloads.
* Preserve event ordering.
* Preserve unknown meta-events.
* Preserve lyric text and encoding information.
* Preserve SysEx payloads.
* Preserve controller and program information.
* Preserve timing precision.

An unmodified import/export round trip should produce semantically equivalent MIDI data.
Byte-for-byte identical output is not required where the MIDI file is legitimately reserialized, but no musical or metadata information should be lost.
Be particularly careful with track-name events and MIDI channel distinctions.
A MIDI track is not the same thing as a MIDI channel.

Suggested project structure:

├── ui/
│   ├── main_window.py
│   ├── timeline.py

│   ├── drag_export.py

│   └── windows.py
├── tests/
│   ├── test_import.py

│   ├── test_timing.py

Treat this as a suggested structure, not a requirement to create unnecessary modules.
Separate the following concerns:

1. Transport/import adapters
2. MIDI parsing and normalization
3. Canonical document model
4. Non-destructive transformations
5. Timeline rendering and interaction
6. Export serialization
7. Operating-system drag-and-drop integration

The core should be independently testable without launching the GUI.

## 11. Packaging
Provide instructions and scripts to build:

* A standalone macOS `.app`
* A standalone Windows application

Use PyInstaller unless a better packaging solution is demonstrably necessary.
Users should not need to install Python, Qt or MIDI libraries separately.
Keep build instructions straightforward.
Development should initially target macOS, with Windows compatibility maintained throughout.
## 12. Development Priorities
Implement in incremental, usable stages.
### Milestone 1 — Functional Vertical Slice
Deliver a running GUI that can:

* Open/drop MIDI files.
* Parse and normalize MIDI.
* Accumulate multiple imports.
* Display tracks and actual note content on a timeline.
* Enable/disable and rename tracks.
* Mark and edit a single export range.
* Export the selected MIDI to a file.

This must be a functional application, not a static UI mock-up.
### Milestone 2 — Interchange
Implement:

* Native drag-in support for external MIDI clips.
* Native drag-out of processed MIDI.
* Multiple imported tracks/clips.
* Individual-track export.
* Source metadata preservation.

### Milestone 3 — Advanced Range Operations
Implement:

* Multiple named ranges.
* Range resizing and repositioning.
* Range concatenation.
* Separate-range export.
* Precise boundary handling.
* Auto-trimming.

### Milestone 4 — Polish and Packaging
Implement:

* Undo/redo.
* Better timeline interaction.
* Keyboard shortcuts.
* Workspace persistence.
* macOS and Windows builds.
* Regression tests and documentation.

## 13. Non-Goals
Do NOT implement:

* Audio playback or rendering.
* Software instruments.
* VST/AU plugin hosting.
* MIDI recording.
* A full piano-roll note editor.
* MIDI effects processing.
* Quantization or humanization.
* A DAW-style mixer.
* An elaborate plugin architecture.
* Cloud services or user accounts.

These are outside the scope of the project.
## 14. Engineering Expectations
The intended developer is an experienced software engineer with extensive C++, C#, Python and low-level systems experience.
Avoid beginner-level explanations and excessive hand-holding.
Make reasonable implementation decisions independently.
Use clear, modular code and established libraries.
Prioritize working functionality, testability and a responsive interface.
Do not spend excessive time debating hypothetical performance limitations or transport-format differences.
When an API has known limitations, identify the actual limitation and implement the appropriate adapter or fallback.
Do not substitute a simplified toy demonstration for the requested application.

Begin implementation of Milestone 1.
First:

1. Briefly confirm the chosen stack and any essential architectural decisions.
2. Identify genuine technical risks or ambiguities that materially affect implementation.
3. Establish the project structure and dependencies.
4. Implement the canonical MIDI document model and SMF import/export.
5. Implement the working PySide6 application with a rendered multitrack timeline.
6. Implement track filtering, renaming and single-range selection/export.
7. Add automated tests.
8. Provide exact instructions to launch the application.

Prefer delivering complete, runnable code over extensive design prose.
Where a feature belongs to a later milestone, leave the architecture capable of accommodating it without overengineering the initial implementation.
Success criterion: I can launch the application, drop in several MIDI files, see their actual musical content on a timeline, disable or rename tracks, mark a range, and export the resulting multitrack MIDI file correctly.
This is the foundation for a fast, practical MIDI interchange utility — not the beginning of another DAW.
